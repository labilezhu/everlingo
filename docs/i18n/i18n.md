# 界面国际化（i18n）设计

本文件是 EverLingo 界面国际化工作的整体路线图与各 Phase 详细方案。

## 范围

需要国际化支持的界面：

- [Web Chatbot](../impl-spec/web-chatbot.md) — Vite + React + shadcn/ui
- [Vault Editor](../impl-spec/vault-editor.md) — 同一 Vite 工程
- [Chrome Extension Sidecar](../impl-spec/chrome-extension-spec.md) — 独立 React 代码副本（`extension/src/components/`）
- [Chat Agent](../impl-spec/chat-agent-spec.md) — Python + langchain，给 LLM 的 system prompt + 少量用户可见兜底文案
- [Vault 目录初始化模板](../impl-spec/vault-mcp/vault-mcp-spec.md) — 建/重置语言知识库时seed 的 `spec/*.md` 规范与目录标题（Phase 6）

## 可用界面语言

当前：`zh-CN`、`en`（两种）。

未来会扩展更多界面语言，并支持前端运行时切换 UI 语言。设计上需为此预留扩展点：

- `可用界面语言` 与 `可用目标学习语言`（`LANGUAGES` 字典 keys：en/ja/zh-CN/fr/de）是**两个独立集合**，语义不同，不可混用。
- 界面语言的「语言代码 → 显示名」映射**复用** `src/everlingo/models.py` 的 `LANGUAGES` 字典（单一真源），不为界面语言另建映射表。
- 可用界面语言以独立常量 `AVAILABLE_INTERFACE_LANGUAGES: tuple[str, ...]` 表达（保序，便于 UI 直接 iterate 展示），定义在 `src/everlingo/models.py`。
- 扩展可用界面语言时只需修改该常量 + 补齐对应 locale 字典，不需动 `LANGUAGES`。

## interface_language 配置语义

`everlingo.yaml` → `user_profile.language.interface_language`：

- **可选**（曾经是必选，本批改为可选）。
- 非空时**必须** ∈ `AVAILABLE_INTERFACE_LANGUAGES`，否则 `UserProfile.validate()` 报错。
- 留空时，运行时按以下顺序推断（`resolve_interface_language()`）：
  1. yaml 值非空且合法 → 直接用；
  2. `locale.getlocale()` 取 OS 语言，归一化（`lower`、`_`→`-`、去编码后缀）后精确命中可用集 → 返回；
  3. 前缀兜底：`zh*` → `zh-CN`，`en*` → `en`；
  4. 仍未命中 → `"en"`。
- **推断值不写回 yaml**。推断仅作运行时兜底；显式值由 onboarding（Phase 3）或 Me 页切换 UI（Phase 3）写入。
- 双访问器（避免推断值污染持久化配置）：
  - `load_profile()` — 返回 raw（interface_language 可能为空或非法），供 `save_profile` / onboarding status / `validate` / conf_manager 等使用。
  - `load_resolved_profile()` — 返回 raw 的副本，`interface_language` 经 `resolve_interface_language()` 填充为非空合法值，供运行时消费者（Agent / Gateway）使用。

### Phase 2 — Chat Agent 兜底文案 i18n（✅ 已完成 2026-08-06）

**目标**：把 `src/everlingo/agents/agent.py` 与 `gateway/` 中给用户看的硬编码中文字符串集中到 `src/everlingo/i18n/messages.py`，按 `profile.language.interface_language` 取对应语言版本。

**边界**：

- **system prompt 本身不动**。`_build_system_prompt()` 的中文指令是给 LLM 看的，LLM 会根据 prompt 里的 `interface_lang` 字段自行决定回复语言，不需要国际化。
- 仅处理**后端直接下发给用户的兜底文案**。注意：下两处文案**不在** Phase 2 范围：
  - 「当前通道不支持语音，请在微信等支持语音的通道使用。」—— 注入在 system prompt 中作为给 LLM 的指令（LLM 负责生成该句），属 system prompt 范畴，不动。
  - 「小记刚才断片了，对话忘记了，笔记还在」—— 前端 `ChatWindow.tsx` 插入的系统通知，属前端文案，Phase 3 处理。

**已迁移的兜底文案**（agent.py / session.py 共 4 处）：

| 位置 | 原中文 | key |
|---|---|---|
| `agent.py` `ainvoke` LLM 调用异常 | 出错了，请稍后重试: {error} | `error_retry` |
| `agent.py` `ainvoke` 重试仍失败 | AI 服务暂时不可用，请稍后重试 (已自动重试 2 次) | `ai_unavailable` |
| `agent.py` `ahandle_system_notice` 异常 | 处理系统通知时出错: {error} | `system_notice_error` |
| `session.py` `_handle_user_message` ainvoke 异常 | 出错了，请稍后重试 | `error_generic` |

**设计要点**：

- 新增 `src/everlingo/i18n/messages.py`：`MESSAGES: dict[str, dict[str, str]]` 按 `{lang: {key: text}}` 组织，`t(key, interface_language, **kwargs) -> str` 取值，缺失 lang 时回退 `en`，缺失 key 时回退 key 本身；`{placeholder}` 由 kwargs 经 `.format()` 填充，占位不匹配时不抛错。
- 取值 lang 来源：`load_resolved_profile().language.interface_language`（Phase 1 已保证非空合法）。`agent.py` 在 `__init__` 与 `_refresh_agent_if_needed()` 重建时维护 `self._interface_lang`；`session.py` 从构造传入的（已 resolved）profile 取。
- 测试：`tests/test_i18n.py`（10 用例，含回退、占位填充、各语言 key 集合一致性）。
- 不在 Phase 2 范围：前端文案 i18n（Phase 3）、system prompt i18n（不做）。

### Phase 3 — Web 前端 i18n 框架 + onboarding step 1 + Me 切换 UI（✅ 已完成 2026-08-06）

**目标**：引入前端 i18n 框架，把 Web Chatbot / Vault Editor / Me 页等界面的硬编码中文文案改为字典驱动；同时新增 onboarding 第一步「选界面语言」与 Me 页「界面语言」切换入口。

**决策记录**：[ADR 20260806-phase3-web-i18n-onboarding.md](../ADR/20260806-phase3-web-i18n-onboarding.md)（解除 [ADR 20260801-user-onboarding.md](../ADR/20260801-user-onboarding.md) §9 的「不引入」决定）。

**设计要点**：

- **i18n 框架**：引入 `react-i18next`（轻量、生态成熟、支持 Suspense 懒加载 namespace）。目录：`web/src/locales/{zh-CN,en}/{common,chatbot,editor,me,onboarding,web-console,login,self-service,pat}.json`。
- **多入口 bootstrap**：`web/` 是 Vite 多 HTML 入口工程，共 8 个独立 React root（chatbot / editor / me / target-language / web-console / login / self-service / pat），并非单一 `main.tsx`。新建 `web/src/i18n/`（`i18n.ts` / `bootstrap.ts` / `detect.ts`）统一入口 `bootstrapI18n()`，所有 8 个 `main.tsx` 调用。
  1. `navigator.language` 启发式推断（`zh*` → `zh-CN`，其它 → `en`）渲染首屏加载占位；
  2. `GET /api/user-profile/status` 取 `interface_language_resolved`；
  3. 若与启发值不同，`i18n.changeLanguage(resolved)` 校正；
  4. 返回 status 供 `main.tsx` 决定后续路由（onboarding 跳转 / 正常渲染）。
  启发式仅用于过渡占位，不写持久化存储；最终生效值始终以服务端 resolved 为准。
- **语言来源**：扩展 `GET /api/user-profile/status` 暴露 `interface_language`（raw）+ `interface_language_resolved` + `available_interface_languages`（含 display 名，复用 `LANGUAGES`）。`is_valid` 字段语义不变（仍只描述 target_language），`needs_setup` 扩展为 `(!is_valid) OR (interface_language == "")`，前端据此决定跳 step 1 还是 step 2。
- **onboarding step 1**：**独立页面** `/console/me/interface-language`，与现有 `/console/me/target-language` 平级。选定界面语言 → `POST /api/user-profile/interface-language` 写入 yaml → 重定向到 step 2。首次运行**强制**跳转 step 1（与 target_language 强制引导语义一致）；OS locale 推断值仅作为 step 1 预选项高亮，用户必须显式确认才写入（推断值不写回 yaml 的不变量保持）。
  - 与 [ADR 20260801-user-onboarding.md](../ADR/20260801-user-onboarding.md) §9「interface_language 的可视化设置」衔接 —— 本 ADR 当时的「不引入」决定在 Phase 3 解除。
- **Me 页切换 UI**：Me 页新增「界面语言」入口（跳转 step 1 同页，普通模式），副标题展示当前 resolved 对应的 display name。
- **写入端点**：`POST /api/user-profile/interface-language`（动作式 POST，与 `POST /api/target-language/default` 风格一致，body `{ lang }`）。写 yaml 后显式调 `bump_prompt_version()` 触发 Agent 重建（interface language 不在 prompt 文件 mtime 监控范围内，必须显式 bump）。**不**回溯给 `set_default_language` 补 bump（已有 mtime 触发机制，改动超出 Phase 3 范围）。
- **运行时切换**：前端 `i18n.changeLanguage()` 即时切换 UI 语言，不需刷新页面；切换并保存后后端 `bump_prompt_version()` 触发 Agent 重建。
- **Vault Editor 一并纳入**：i18n.md 原「不在范围」仅排除 Chrome Extension。Vault Editor（`web/src/editor/`，约 50+ 处中文）与 Chatbot 共享同一 Vite 工程与 `i18n` 实例，应一并 i18n 以避免「半国际化」状态。Editor 的 `main.tsx` 同样接入 `bootstrapI18n()`。
- **前端测试**：引入 vitest + @testing-library/react + jsdom；测试 i18n 字典一致性（zh-CN/en key 深度相等、占位符一致）、bootstrap 顺序、step 1 页交互。
- **PWA / shadcn 兼容**：react-i18next 与现有技术栈无冲突；两份 JSON 字典 ≈ 10~30KB，可接受。

- Chrome Extension i18n → Phase 4
- Chat Agent 兜底文案（已在 Phase 2 处理）
- system prompt 本身 i18n → 不做（LLM 按 prompt 中 `interface_lang` 字段自行决定回复语言）
- 回溯给 `set_default_language` 补 `bump_prompt_version()` → 超出范围，不动现有重建时机

### Phase 4 — Chrome Extension i18n（✅ 已完成 2026-08-07）

**目标**：Chrome Extension Sidecar 的 UI 文案国际化。

**设计要点**：

- Extension 是 web 组件的独立副本（见 [chrome-extension-spec.md §3 代码位置](../impl-spec/chrome-extension-spec.md)），按现有「独立维护」策略，**复制 `web/src/locales/` 到 `extension/src/locales/`**，同样引入 `react-i18next`。
- 语言来源：extension 启动时已有 `server_url`/`device_id` 等配置；新增 `interface_language` 到 `chrome.storage.local`（首次创建 session 时由后端返回并缓存），与 `device_id` 同生命周期。
- **不引入** `_locales/` + `chrome.i18n`（那是给扩展 UI manifest 用的，与 React 内文案体系不一致）。

**实现说明**（已完成）：

- **后端**：`src/everlingo/gateway/gateway.py` 新增 `Gateway.interface_language` property（暴露当前 resolved 界面语言）；`POST /api/session`（`web_acceptor.py` `create_session`）返回新增 `interface_language` 字段。ws_router 多用户拓扑将 `/api/*` 代理到工作区 web_acceptor，故该响应经代理转发自动生效，无需改 ws_router。
- **依赖**：extension 引入 `i18next` + `react-i18next`（与 web 一致）。**background service worker 不引 react-i18next**（避免 SW 包膨胀），其右键菜单文案由 `extension/src/i18n/menu.ts` 轻量字典 `contextMenuTitle(lang)` 提供。
- **字典**：`extension/src/locales/{zh-CN,en}/` 复制自 web（9 namespace），并新增 extension 独有的 `options.json`（OptionsForm 设置页，无 web 对应）；runtime 仅装配 `common` / `chatbot` / `options` 三个 namespace。
- **引导**：`extension/src/i18n/{i18n,detect,bootstrap}.ts` —— `bootstrapI18n()` 读取 `chrome.storage.local` 的缓存 `interface_language`，经 `resolveSupportedLang()` 校验（非法/空回退 `navigator` 启发值 zh→zh-CN / en），`initI18n()` 初始化；`sidecar.tsx` 与 `options.tsx` 两个入口在 render 前 `await bootstrapI18n()`。
- **语言缓存**：`extension/src/config.ts` 新增 `INTERFACE_LANGUAGE_STORAGE_KEY` + `getStoredInterfaceLanguage()` / `setStoredInterfaceLanguage()`；`background.ts` 在 `createSession()` 拿到后端返回的 `interface_language` 后缓存，并 `chrome.contextMenus.update` 同步右键菜单标题。
- **文案迁移**：ChatWindow（欢迎语 / 各错误提示 / 状态条 / 思考中 / app 名 / 笔记）、ChatInput（placeholder / 发送）、MessageBubble（语音消息）、TaskSelector（翻译 / 查词 / 聊天）、OptionsForm（全部设置字段与测试文案）迁移到字典；`normalizeUrl` 错误改为抛 `UrlFormatError`（带稳定 name），OptionsForm 据此映射为本地化文案，避免在非 React 的 `config.ts` 引入 i18n。
- **测试**：`extension/src/i18n/i18n.test.ts`（9 用例：zh/en 各 namespace 深度 key 一致性、占位符一致、`resolveSupportedLang`、右键菜单回退）；`config.test.ts` 增补 `UrlFormatError` 断言。

**不在 Phase 4 范围**：Chrome Extension MV3 `manifest.json` 的 `name` / `description` i18n（继续不引入 `chrome.i18n`，见 Phase 5）。

### Phase 5 — PWA 信息 i18n（manifest + apple-mobile-web-app-title）

**目标**：把 `web/public/manifest.webmanifest` 的 `name` / `short_name` / `description` 与 9 个 HTML 入口的 `<meta name="apple-mobile-web-app-title">` 纳入 i18n，按请求语言动态协商，英文界面用户安装 PWA 后看到英文应用名。

**决策记录**：[ADR 20260807-pwa-i18n.md](../ADR/20260807-pwa-i18n.md)

**设计要点**：

- **范围**：仅 web PWA manifest（`web/public/manifest.webmanifest`）与 9 个 `web/*.html` 的 `apple-mobile-web-app-title`。**不**含 Chrome Extension MV3 `manifest.json`（继续按 Phase 4 既定决策不引入 `chrome.i18n`）。
- **文案真源**：后端 `src/everlingo/i18n/pwa.py` 的 `PWA_MANIFEST_TEXT: dict[str, dict[str, str]]`（与 Phase 2 的 `messages.py` 同目录同模式）；前端 `web/src/locales/` 不动（manifest 由后端服务，非前端 React 渲染）。
- **语言协商**：新增 `resolve_manifest_language(accept_language, interface_language=None) -> str`，优先级：
  1. `interface_language` 非空且 ∈ `AVAILABLE_INTERFACE_LANGUAGES` → 直接用（仅 web_acceptor 传）
  2. `parse_accept_language(accept_language)` 解析 HTTP `Accept-Language` 头（q-value），首个命中可用集或前缀命中（`zh*`→`zh-CN`、`en*`→`en`）→ 返回
  3. 兜底 `"en"`
- **架构约束**：ws_router（多用户部署）的 manifest 端点在 pre-auth 白名单内（[ws-router.md:181](../impl-spec/multiple-users/ws-router.md)），绕过认证，不持有 user profile，**仅用 Accept-Language**；web_acceptor（单机 / ws-container 内）可读 `load_profile()`，**profile 优先 + Accept-Language 兜底**。这是可接受的折中：登录后浏览器仍带 Accept-Language，manifest 与浏览器语言一致；与用户 onboarding 选的界面语言可能不同，但 manifest 语言一旦在安装时确定后浏览器会缓存。
- **manifest 端点动态化**：`web/public/manifest.webmanifest` 删除 `name` / `short_name` / `description` 三字段（仅保留语言无关字段 `start_url` / `scope` / `display` / `orientation` / `background_color` / `theme_color` / `icons`）；服务端 `_serve_manifest(request)` 读该文件 + 合并 `PWA_MANIFEST_TEXT[lang]` 三字段 + 动态 `json.dumps` 返回。响应头 `Cache-Control: no-cache`（保留 ADR 20260804）+ **新增 `Vary: Accept-Language`**。
- **HTML 占位符替换**：9 个 `web/*.html` 的 `<meta name="apple-mobile-web-app-title" content="小记">` 改为 `content="{{pwa_short_name}}"`（Vite 不处理 meta content，占位符原样保留到 `web/dist/*.html`）；服务端 `_serve_html_with_i18n()` 读 HTML 字符串 → 按 `resolve_manifest_language()` 取 `short_name` → `str.replace("{{pwa_short_name}}", short_name)` → 返回。不引入 Jinja2（仅一处占位符，字符串替换足够）。HTML 响应头新增 `Vary: Accept-Language`。
- **`models.py` 重构**：`resolve_interface_language()` 的归一化逻辑（`lower` / `_`→`-` / 去编码后缀）提取为内部 helper `_normalize_lang_tag()`，供 `parse_accept_language()` 复用；主函数行为不变（向后兼容）。
- **`short_name` 与前端 `app_name` 独立**：不复用 `web/src/locales/*/chatbot.json` 的 `app_name`（避免后端读前端 JSON 的跨层耦合；short_name 可能受 12 字符限制，未来与 chatbot 标题分化）。
- **测试**：`tests/test_i18n_pwa.py` —— `parse_accept_language` 各情形、`resolve_manifest_language` 优先级、web_acceptor manifest 端点（profile 优先 / Accept-Language 兜底 / Vary 头）、HTML 占位符替换；ws_router manifest 端点（不同 Accept-Language 返回不同 name、Vary 头）。

**改动清单**：

#### 源码

1. `src/everlingo/i18n/pwa.py`（新建）：`PWA_MANIFEST_TEXT` + `parse_accept_language()` + `resolve_manifest_language()`。
2. `src/everlingo/models.py`：`resolve_interface_language()` 提取 `_normalize_lang_tag()` helper（行为不变）。
3. `src/everlingo/ws_router/app.py`：manifest 分支改 `_serve_manifest(request)`（仅 Accept-Language）；HTML 入口（`/login`、`/self-service`、`/self-service/pat`）改 `_serve_html_with_i18n()`。
4. `src/everlingo/gateway/web_acceptor.py`：manifest 端点改 `_serve_manifest(request)`（传 profile）；HTML 入口（`/editor`、`/console/me`、`/console/me/target-language`、`/console/me/interface-language`、`/console/web-console`、`/` catch-all）改 `_serve_html_with_i18n()`。
5. `web/public/manifest.webmanifest`：删 `name` / `short_name` / `description`。
6. `web/*.html`（9 个）：`apple-mobile-web-app-title` content 改 `{{pwa_short_name}}`。

#### 测试

- `tests/test_i18n_pwa.py`（新建）。
- ws_router manifest 端点测试（扩展或新建）。

#### 文档

- `docs/ADR/20260807-pwa-i18n.md`（本 Phase）
- `docs/i18n/i18n.md`（本文件）
- `docs/impl-spec/web-chatbot.md` §PWA
- `docs/impl-spec/multiple-users/ws-router.md` §4
- `docs/impl-spec/web-session-acceptor.md`
- `TASKS.md`、release notes

#### 不在 Phase 5 范围

- Chrome Extension MV3 `manifest.json` 的 `name` / `description` i18n（继续按 Phase 4 既定决策「不引入 `chrome.i18n`」）。
- Service Worker / 离线能力（仍不引入，见 [ADR 20260804 §5](../ADR/20260804-web-cache-control.md)）。
- manifest 语言写回用户配置（manifest 语言仅为运行时协商结果，不反向更新 profile）。
- `theme_color` / `icons` 随语言变化（当前语言无关；如未来需要按语言出不同图标，再扩展）。

### Phase 6 — Vault 目录初始化模板 i18n（✅ 已完成 2026-08-08）

**目标**：把 `create_vault` / `reset_vault` / `session.configure` 用于初始化 `$workspace/memory/languages/$lang/vault/` 的模板（`spec/*.md` 规范 + `items/**/index.md`、`events/index.md`、`index.md` 目录标题）按 `可用界面语言` 拆分，运行时按 `interface_language` 选择对应语言的模板初始化。

**决策记录**：[ADR 20260808-vault-template-i18n.md](../ADR/20260808-vault-template-i18n.md)

**设计要点**：

- **模板组织**：`src/everlingo/mem/vault/templates/default/` 拆分为 `en/`、`zh-CN/`（保留 `default` 这层，未来可扩展其它模板族）。原中文内容移至 `zh-CN/`，新译英文放 `en/`。两份模板的相对路径树保持一致（测试断言）。
- **server 端语言解析**：新增 `_resolve_template_lang(interface_language)` —— 复用 `resolve_interface_language()`（精确命中 → OS locale 推断 → 前缀兜底 → en），并加「模板子包存在性」检查，缺失回退 `en`。`create_vault` / `reset_vault` 的 `PackageSource` 与遍历根按所选语言子包拼接。
- **幂等语义不变**：`create_vault` 对已存在文件不覆盖（存量 vault 不受影响）；`reset_vault` 仅覆盖写 `spec/*.md`，用当前界面语言重 seed。缺省（未传 `interface_language`）时在 server 内按 OS locale 推断。
- **`session.configure`**：已有 `interface_language` 参数，自动创建缺失 vault 时透传给 `create_vault`。
- **调用链**：后端显式传 resolved 界面语言。Memory Writer：`entry.interface_language`；Chat Agent：`self._interface_lang`；Vault Editor：`load_resolved_profile()` 兜底；`POST /api/target-language/{default,reset-vault}`：`load_resolved_profile()`。
- **spec include 展开**：`spec/*.md`（无 frontmatter）走 `compile_prompt + PackageSource`，include 相对路径在所选语言子包内解析；`spec/index.md` 与 items 目录 index 有 frontmatter，raw copy。

**改动清单**：

#### 模板

- `templates/default/` → 拆 `en/` + `zh-CN/`（英文为翻译版，路径树一致）。

#### 源码

1. `src/everlingo/mem/vault/mcp_server/mcp_server.py`：新增 `_resolve_template_lang()`；`create_vault_tool` / `reset_vault_tool` 增可选 `interface_language` 参数并按 `_resolve_template_lang` 选子包；`session.configure` 自动建 vault 时透传 `interface_language`。
2. `src/everlingo/mem/agents/mem_writer_mcp_client.py`：`mcp_vault_connection` 增 `interface_language` 参数并传入 `session.configure`。
3. `src/everlingo/mem/agents/mem_writer_agent.py`：6 处 `mcp_vault_connection(entry.lang)` 传 `entry.interface_language`。
4. `src/everlingo/agents/agent.py`：Chat Agent 建 vault 上下文传 `self._interface_lang`。
5. `src/everlingo/gateway/vault_editor_mcp_client.py`：`mcp_session_configured` 增 `interface_language`。
6. `src/everlingo/gateway/vault_editor_api.py`：`_configured` 未传时用 `load_resolved_profile()` 兜底。
7. `src/everlingo/gateway/user_profile_api.py`：`POST /api/target-language/default`（create_vault）与 `reset-vault` 传 `load_resolved_profile()` 的界面语言。

#### 测试

- `tests/test_mem_vault_mcp_server.py`：en/zh-CN 模板实例化内容断言、OS locale 推断模板语言、前缀/locale 兜底、模板缺失回退 en、reset 用新语言重 seed、session.configure 透传、双层模板路径树一致性（新增 8 用例）。
- 既有用例改为显式 `interface_language="zh-CN"`（不依赖 OS locale 语义）；conftest / 其它测试的模板包引用改为 `templates.default.zh-CN.spec`。

#### 文档

- `docs/i18n/i18n.md`（本文件 Phase 6）

#### 不在 Phase 6 范围

- Vault 里 LLM 生成的条目正文语言：由 LLM 依据 prompt / interface_lang 决定，不在此列。
- 对存量已初始化 vault 的语言迁移（`create_vault` 幂等不覆盖；如需换语言由用户 `reset_vault` 显式触发）。
- 更多界面语言模板（当前仅 en / zh-CN；未来扩展时新增对应模板子目录即可）。

#### Phase 6 补记（i18n 检漏，2026-08-08）

- **events 文件前置内容纳入 i18n 字典**：当日 events 文件（`events/<YYYY>/<MM>/<date>.md`）首次创建时由代码写入的「文件前置内容」此前硬编码在 `mem_writer_agent.py`，随 `interface_language=en` 仍输出中文。现移入 `src/everlingo/i18n/vault.py`（`EVENT_FILE_PREAMBLE` zh-CN/en + `event_file_preamble(interface_language)`），由 `_append_event_async` / `_append_action_event_async` 按 `entry.interface_language` 选择。与模板文件不同，该内容是运行期代码写入，故单独建字典而非模板子包。
- **`why_want_to_save_memory` 改为 LLM 自由文本**：原为中文枚举（`用户明确要求记住知识点` / `纠正事项` / `Chat Agent 判定`），属界面语言相关数据但硬编码中文。现改为 `str`（`mem_entries.py` 删 `WhySave` Literal、`request_memory_extract.py` 删 Literal），由 LLM 按界面语言写一句简短原因，程序不按枚举处理；`agent.py` prompt 与 `mem_entry_spec.md`（现为 `src/everlingo/agents/spec/` 代码资产，仅 zh-CN）字段说明同步改自由表述。
