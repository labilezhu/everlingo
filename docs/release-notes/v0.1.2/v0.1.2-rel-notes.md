# 🎉 EverLingo v0.1.2 release notes

## New Features

- Added Memory Vault version control and remote backup: `$workspace/memory` is now a git repository, with an in-process committer that auto-commits at a configurable interval and pushes to the user's own git remote (`ssh` / `https_pat` / `https_none`), so accidental deletions are traceable and vaults are recoverable on another machine.
- Added CLI commands `everlingo mem snapshot / push / pull / restore / log / vstatus` that delegate to the running indexer over its HTTP endpoints (`/version/*`), enabling manual commits, force-with-lease push, remote restore, and history browsing.

## New Features (Multi-User · WS-Master)

- WS-Master now supports forwarding environment variables to dynamically created ws-containers: any variable prefixed with `WS_CONTAINER_` in the ws-master process environment is injected into the ws-container with the prefix stripped (passthrough takes precedence over explicitly-injected env). For example, setting `WS_CONTAINER_HTTP_PROXY` / `WS_CONTAINER_HTTPS_PROXY` / `WS_CONTAINER_NO_PROXY` on the compose `ws_master` service lets ws-containers reach OpenAI / OpenRouter through a corporate proxy without changing the image.

## Enhancements

- `reset_vault` now snapshots the current vault changes into git history before overwriting template specs, so user edits are never silently lost.
- `user_doc_set` no longer writes a `USER.md.bak` backup: history is now maintained by the Memory Vault git repo instead.

## Internal Changes

- Added `src/everlingo/mem/vault/version/` package: `git.py` (subprocess git CLI wrapper: init/status/commit/push/fetch/rebase/log/branch/reset, always passing `-c safe.directory` for uid-mismatched mounted workspaces), `committer.py` (timer-based auto-commit with debounce + push interval, initial-commit fallback and atexit/stop final commit), `ssh_key.py` (temporary private-key lifecycle + `GIT_SSH_COMMAND` injection with `StrictHostKeyChecking=accept-new`), and `restore.py` (commit → fetch → rebase, conflicts preserved into a `backup/restore-<ts>` branch without touching the working tree).
- Added `git_backup` configuration section to `everlingo.yaml` (`enabled` / `remote_url` / `branch` / `auth` / `commit_interval` / `push_interval`) with `setting.load_git_backup()` / `save_git_backup()`.
- Indexer `AppState` now owns a `Committer` that is started/stopped with the process lifespan; `git init` is lazy on first startup and performs an initial commit capturing existing vault content.
- Indexer HTTP adds `/version/status`, `/version/commit`, `/version/push`, `/version/pull`, `/version/log`, and `/version/restore` endpoints; the SearchClient gains matching methods.
- The indexer startup now force-renames the local git branch to the configured `branch` (`git branch -M`), so Memory Vault repos initialized on other machines or by hand stay consistent for push / fetch-rebase / status regardless of the original branch name.

## New Features (Phase 2 · P3)

- Added a backup configuration page `/console/me/backup` (always visible from the Me page): repo status (initialized / dirty / last commit / ahead-behind / remote URL / branch), a configuration form (toggle / remote URL / branch / SSH key), action buttons (test connection / snapshot now / push now / pull & rebase / hard reset with confirmation), and a commit history list.
- Added gateway REST API `/api/backup/*` (status/config/snapshot/push/pull/test/reset-hard/log/restore) that delegates to the indexer `/version/*` endpoints over the unix socket and reads/writes the `git_backup` section of `everlingo.yaml`.

## New Features (Phase 2 · P3 · Force Push)

- Added a "force push" action that runs `git push --force` (unconditionally overwriting remote history, confirmed via dialog in the UI): new `/version/force-push` and `/api/backup/force-push` endpoints, a "Force push" button next to "Push now" on the backup page, and the `everlingo mem force-push` CLI command.

## Enhancements (Phase 2 · P3)

- Configuration now takes effect immediately: new `/version/apply-config` endpoint together with `Committer.apply_config()`/`reload_config()` start/stop the committer timer thread and reconfigure the SSH context without restarting the indexer.
- Added "test connection": a read-only `git ls-remote` probe against the configured remote (reusing `git_backup` credentials), exposed via `/version/test`.
- Added a "hard reset to remote" action: `/version/reset-hard` runs `git reset --hard origin/<branch>` with an explicit confirm step in the UI (backup-branch fallback from `restore.py` is preserved for conflicted restore flows).

## Enhancements (Phase 2 · P3 · i18n)

- User-visible messages of the Memory Vault version-control backend are now internationalized: `GitError` messages (`git.py`), `test_remote` results, `RestoreResult.message` (`restore.py`), committer push errors, indexer `/version/*` HTTP error details, and the gateway `backup_api.py` 503 / auth-method messages follow the interface language (`zh-CN` / `en`, fallback `en`). Git CLI stderr output is kept verbatim (English), and backend `logger.*` messages are excluded.
- New `src/everlingo/i18n/version.py` (`VERSION_MESSAGES` + `version_t`) follows the Phase 2 `messages.py` pattern; low-level git functions accept an optional `interface_language` parameter (defaults to `en`), indexer endpoints and `backup_api.py` resolve the language via `load_resolved_profile()`, and background committer pushes fall back to the resolved profile language.
## New Features (Chat Image · Phase 1)

- Web Chatbot now supports uploading an image (file picker / paste screenshot / camera) and sending it together with a chat message: the image is stored on the backend and referenced from the message envelope (`chat.attachments[].src_resource_sha256`), and the uploaded image is rendered immediately in the user bubble.
- Added `PUT /api/session/{session_id}/images/{src_resource_sha256}` (multipart) which validates MIME (jpeg/png/webp) and SHA-256, stores the bytes under `{workspace}/sessions/{session_id}/images/{sha256}.{ext}`, and returns the `ImageAsset` metadata; re-uploading the same image is idempotent.
- Added the `ImageStore` abstraction (`src/everlingo/image/`) so the backend can later swap local filesystem storage for real object storage without changing callers; the message endpoint enforces at most 1 image per message for the MVP.

## Internal Changes (Chat Image · Phase 1)

- Extended the envelope schema with `chat.attachments[]` (`src_resource_sha256` + `type`) on both the Python (`AttachmentPart` / `ChatPart.attachments`) and TypeScript sides; the Chat Agent does not consume attachments yet (Phase 2/3 will add the Vision analysis tool).

## New Features (Chat Image · Phase 2)

- Added a Vision Service layer (`OpenRouterVisionService`) that reads the stored image bytes and runs them through a vision-capable OpenRouter model (`xiaomi/mimo-v2.5` by default, configurable) to produce a structured `ImageAnalysis` (OCR `text` + business-level `structured_content` + `knowledge_points`). It follows the ADR principle that Vision only answers "what is in the image" and never outputs answers or explanations.
- Vision results are cached in-process with an LRU + 7-day TTL keyed by `src_resource_sha256 + model + prompt version`, shared across all users, so a hot learning image (e.g. a common English exercise) is analyzed at most once; a concurrency guard dedupes simultaneous analysis of the same image into a single Vision Model call.
- Image upload now eagerly warms the Vision cache in the background (fire-and-forget, non-blocking, failure silent), so the agent tool usually hits the cache and first response latency drops.

## Internal Changes (Chat Image · Phase 2/3)

- Image uploads are now preprocessed with Pillow on save: EXIF orientation correction first, metadata stripping, then proportional rescaling to at most 1920x1200 pixels; `saved_resource_sha256` recomputed from processed bytes, `width`/`height` populated. New dependency: `pillow`.
- Added `VisionPurpose` (ocr / exercise / document / learning_content / general) and the `ImageInput` reference model; `ImageAnalysis.structured_content` is intentionally a loose dict to accommodate varying content shapes.
- New `analyze_image` tool (`make_vision_tool`) registered for image-capable channels (web): the agent calls it with an `src_resource_sha256` from the envelope and receives the `ImageAnalysis` as a tool message. On Vision failure the tool returns a friendly degradation message instead of raising (ADR error codes `VISION_MODEL_UNAVAILABLE` / `VISION_ANALYSIS_FAILED` / `VISION_OUTPUT_INVALID`).
- New `get_vision_llm_config()` / `vision_model` setting (`setting.sys_setting.vision_model` / env `VISION_MODEL`, default `xiaomi/mimo-v2.5`) and `create_vision_llm()` (temperature 0, request timeout 120s); `ChannelMetadata` gains `supported_image` (web channel sets it).

## Docs

- Promoted the implemented image-store and vision-service design from the ADR into formal implementation specs: new `docs/impl-spec/vision/image-store-spec.md` (data models, storage layout, front-end `PUT /api/session/{session_id}/images/{src_sha}` upload endpoint contract, Pillow preprocessing, error mapping, lifecycle) and `docs/impl-spec/vision/vision-service-spec.md` (perception boundary, `ImageAnalysis`, caching/concurrency guard, Eager Warm + tool-fetch hybrid, `analyze_image` tool wiring, error codes).

## New Features (Vault Image · Backend)

- The Vault Editor backend now supports inserting images into markdown notes: new `save_vault_image()` in `image_store.py` writes image bytes into a relative path inside the language vault (reusing EXIF correction / metadata stripping / downscaling preprocessing), validates that the file-name stem matches the recomputed SHA-256, embeds its own provenance metadata (JPEG EXIF UserComment / PNG tEXt `src_resource_sha256=...`), and is idempotent per path.
- Added `GET`/`PUT /api/vault/raw/{lang}/{vault_rel_path:path}`: PUT uploads a multipart `file` field (MIME allow-list 415, empty file / sha mismatch / path escape / invalid image data 400, idempotent re-upload) and returns the `ImageAsset` metadata; GET serves any vault file with extension-based `Content-Type` (images inline, text as `text/plain`, others `application/octet-stream`) plus an immutable cache header. Both endpoints enforce the same resolve + `is_relative_to(vault_root)` trust boundary as the existing `read` endpoint.

## Docs (Vault Image · Backend)

- Added the "Vault image storage" section to `docs/impl-spec/vision/image-store-spec.md` describing `save_vault_image` (validation, preprocessing + self-metadata, path-based idempotency, `memory://languages/{lang}/vault/...` storage key).
